## 5. 固定技术路线

### 5.1 总体架构

采用模块化单体，先保证领域边界、事务和交付效率，不提前拆微服务：

```text
Vue 3 + TypeScript + Element Plus
             ↓ 类型化 API / OpenAPI
Spring Boot 模块化单体
  ├─ IAM / Organization
  ├─ Property / Customer
  ├─ Fee / Receivable
  ├─ Cashier / Ledger
  ├─ Metering
  ├─ Reporting / Printing
  ├─ Migration / Integration
  └─ Audit / Task
             ↓
MySQL 8 + Redis + 文件/对象存储抽象
```

### 5.2 已冻结决策

- 前端：Vue 3、TypeScript、Vite、Element Plus、Pinia、Vue Router；
- 后端：Java 17、Spring Boot 模块化单体、Spring Security、Flyway；
- 数据：MySQL 8，金额使用 Decimal，时间和枚举采用稳定格式；
- 缓存/锁：Redis；
- 运行：Docker Compose，一套命令可从空环境启动；
- API：`/api/v1`、稳定错误码、显式 DTO、Bean Validation、乐观锁；
- 核心写接口：幂等、权限、审计、并发保护和可追踪请求 ID；
- 财务：成功流水不可物理删除，退款/冲正/调账使用关联反向流水；
- 外部集成：端口/适配器；模拟和真实通道必须在配置与 UI 中明显区分；
- UI：复刻信息架构、密度和工作方式，使用中性自有品牌，不复制目标资源。

### 5.3 Spring Boot 升级决策

当前工程保持 Spring Boot 2.7 可运行基线。在 G1 结束前形成升级 ADR，验证依赖、Jakarta 迁移、Java110 适配和测试成本；若升级到受支持的 Spring Boot 3.x 不破坏交付，则在独立检查点完成。不得在同一批同时大规模升级框架和改写财务业务。

## 7. 每页统一完成定义

每一个范围页面只有同时满足以下条件才可在追踪矩阵中标为完成：

1. 有稳定路由、菜单和页面级/按钮级权限；

5. 核心页面使用专用 DTO、领域服务和数据库约束，不依赖无边界 Map 写入；
6. 写操作具备权限、幂等/乐观锁、审计和稳定错误语义；
7. 需要的批量、导入、导出、打印或任务结果为真实可运行能力；
8. 涉及个人信息时具备脱敏、导出控制和审计；
9. 至少有与风险相称的单元、组件、API、E2E 或视觉测试；

## 9. 数据使用与迁移原则

### 9.1 数据分级

| 级别 | 内容 | Goal 内处理 |
|---|---|---|
| C0 结构 | 菜单、字段、枚举 | 可用于结构分析，记录来源和版本 |
| C1 配置 | 费用定义、字典、模板 | 授权后可迁移，必须版本化和审核 |
| C2 资产 | 楼栋、房屋、车位、仪表 | 开发使用假名/脱敏数据；正式迁移需审计和对账 |
| C3 个人信息 | 姓名、电话、证件、住址、访客 | 不进入普通开发库；最小化、加密、脱敏和保留期限 |
| C4 财务/税务 | 应收、实收、预收、押金、发票、银行 | 开发仅使用合成/批准样本；正式迁移需双人复核 |
| C5 秘密 | 密码、Token、密钥、证书 | 禁止进源码、Git、迁移文件、日志和文档 |

### 9.2 正式数据来源

只接受数据所有方批准的官方导出、API 或数据库只读副本。不通过页面抓取直接复制真实客户和财务数据。目标站登录凭据只能由本地忽略的环境配置或安全存储使用，不写进源码和计划。

### 9.3 对账维度

- 数量：企业、项目、组织、楼栋、单元、资产、客户、关系、仪表、费用、账单和流水；
- 关系：孤儿、重复有效关系、唯一键冲突均为 0；
- 面积：按项目、楼栋和资产类型汇总；
- 金额：按账期、费用、资产、客户、支付方式、收款员和状态汇总；
- 恒等式：应收、已收、未收、调整、预收、押金和冲正余额守恒；
- 时间：全量截止点和增量无丢失、无重复；
- 报表：金标准月份的汇总和明细一致；
- 抽样：高风险数据保留业务、财务和技术复核记录。

## 13. Goal 每轮执行规则

每轮自动续作遵循同一循环：

1. 读取当前 Goal、本文、实施日志、Git 状态和上一检查点；
2. 从当前阶段选择一个能够独立验收的纵向工作包；
3. 先检查现有用户改动和依赖，不覆盖、不重置；
4. 同批完成数据库、后端、前端、权限、测试和文档，不制造长期断层；
5. 运行与风险相称的最小验证，检查点结束运行该阶段全套验证；
6. 更新追踪矩阵、实施日志、已知差距和验收证据；
7. 只提交本批相关改动，记录提交、测试、数据变化和下一工作包；
8. 若失败，先诊断和修复，不把失败推迟到最终验收；
9. 若出现真实外部阻塞，继续推进所有不受阻塞影响的内部工作；
10. 仅在第 12 节全部满足时标记 Goal 完成。

每个检查点应保持：应用可启动、数据库可迁移、自动化主干全绿、合成数据可重建、文档与实现一致。
