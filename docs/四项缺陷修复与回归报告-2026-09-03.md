## 2. 修复详情

### 2.1 报表筛选条件失效或映射错误

根因有三层：

1. 旧前端把所有普通筛选值压缩成 `status`，把日期范围统一改成 `from/to`，把账期改成 `periodFrom/periodTo`；字段原名因此丢失。
2. 部分选择型字段使用自由文本输入，页面无法保证发送后端接受的枚举值或项目内 ID。
3. 后端虽然收到任意查询参数，但没有对 22 个报表建立统一的字段允许表、类型校验和项目范围校验；部分 SQL 也没有真正使用页面显示的条件。

实施内容：

- 新增 `apps/admin-web/src/config/reportFilters.ts`，根据页面查询 schema 保留 `transactionNo`、`paymentChannel`、`feeDefinitionId` 等标量字段原名，并将日期/月份范围序列化为明确的 `dateFrom/dateTo`、`billingPeriodFrom/billingPeriodTo` 等契约。
- 查询按钮统一先回到第 1 页再请求，避免用户在高页码切换条件后误判为空。
- 枚举字段改为受控下拉；费用定义和收银员通过 `/reports/filter-options` 动态加载。选项按当前项目和当前报表权限裁剪，并保留仍被历史流水引用的停用值。
- 保存的筛选快照以“当前项目 + 报表路由”隔离，恢复时采用白名单后的完整替换而非与旧状态合并；损坏快照会被清理，项目之间不会串用费用定义、收银员或其他条件。
- 项目切换会立即清空旧结果、任务和筛选选项，并以请求代次校验丢弃晚到的旧项目响应；看板采用同样机制，避免网络乱序把上一个项目的数据覆盖到当前项目。
- 后端为 22 个报表建立字段 allowlist、枚举 allowlist、严格日期/月份解析、范围顺序校验、项目内费用定义/收银员 ID 校验；未知字段、非法枚举、越权 ID 和无效日期均拒绝，不再静默忽略。
- OpenAPI 显式声明所有筛选参数，前端生成类型与运行中 API 已重新同步。
- 修正各报表 SQL 的日期、账期、渠道、状态、关键字和费用定义映射；费用口径按账单项目占比分摊实收，并在清欠率、收清欠汇总和收费明细中纳入冲正/退款的有符号账本变动，避免只累计正向收款。
- 最终审计进一步限定折扣明细只纳入 `APPLIED` 调账，并统一按实际应用/批准时间筛选、展示和排序；`PENDING`、`REJECTED` 以及创建时间落入但生效时间越界的记录均不会进入报表。
- 异步导出提交当前 UI 可见列，不再用空数组隐式展开 `billId`、`receiptId` 等非展示业务键；查询响应仍保留批量打印需要的隐藏收据 ID。
- 分页偏移改为 64 位安全计算；极大合法页码只返回空页，不会因 32 位乘法溢出产生 500。
- V21 对齐报表筛选元数据；由于 V21 已在既有运行库执行，后续修正采用只追加的 V22 迁移，没有改写已执行迁移历史。

### 2.2 API/Web OpenSSL High 漏洞

实施内容：

- API 和 Web 运行镜像在构建时执行 Alpine 安全更新，并显式要求 `libcrypto3`、`libssl3`（API 另含 `openssl`）不低于 `3.5.8-r0`；仓库无法提供该版本时构建直接失败。
- 安全候选使用 `docker compose build --pull --no-cache` 重建，避免基础镜像或 APK 缓存继续复用旧补丁层。
- API 继续以 UID 100 运行，Web 以 UID 101 运行；API 内嵌 Tomcat 固定为 10.1.59。
- 生产 Compose 改为不可变镜像摘要、仓库外文件 Secret、统一目标平台、三网隔离和只绑定 loopback 的 Web 端口。API/MySQL/Redis 不发布宿主端口，API 不具备默认公网出口。
- 生产验证器同时拒绝 `privileged`、额外 capability、设备、host namespace、Docker socket、任意宿主 bind 和伪装 bind；运行态会重新核对容器权限及完整挂载集合。Web 发布端口固定为 5174，与宿主 TLS upstream 保持单一契约，其他端口会被门禁拒绝。
- 三个生产网络必须使用当前 Compose project 的精确名称、本地 bridge 驱动和批准的 internal 属性，禁止改成 external/shared 网络；运行态继续核对 driver、scope、attachable 和 Compose 所有权标签。
- API/Web/Redis command、API/Web/MySQL entrypoint、MySQL command、Redis ACL bootstrap 以及四项 healthcheck 均有静态完整值和部署态最终进程双重校验，不能保留已扫描镜像却改跑其他命令或恒真探针。
- 生产登录锁定固定为 5 次失败、15 分钟窗口、15 分钟锁定，并由 Jakarta Validation 在应用绑定层拒绝零值和越界值。
- API 生产环境变量采用精确白名单并锁定高风险值；部署后把“镜像默认 Env + 已验证 Compose Env”与容器实际 Env 逐键比较，阻断 `SPRING_APPLICATION_JSON`、Java 启动选项或 `PMS_SECURITY_*` 对 Secret 和安全属性的旁路覆盖。
- 宿主 TLS 入口覆盖客户端伪造的 `X-Forwarded-For` 并清空 `Forwarded`，内部 Web 代理只转发受控来源；Linux smoke 和部署后门禁直接读取 `/proc/1/status`，确保四项服务 PID 1 均非 root。
- Redis 生产 ACL 限定 `pms3:*` key 和明确命令白名单；危险、管理和发布订阅能力保持禁用。
- 扫描器升级为 schema v3 证据：绑定 image ID、digest、平台、原始 Trivy 文件 SHA-256、扫描目标和包清单；验证器从原始报告重算，缺字段、空目标、报告篡改或非零 Critical/High 均失败关闭。

### 2.3 30 条费用分配孤儿误报

根因是 `fee_allocation` 是多态目标表：`target_type='ASSET'` 时关联 `asset_id`，`target_type='METER'` 时关联 `meter_id`。旧看板一律左连接 `asset`，因此 30 条合法仪表分配被当成缺失资产。

修复后：

- 分配总数直接按 `fee_allocation.community_id` 统计。
- 同时返回 `asset_allocations` 和 `meter_allocations`，前端明确显示两类数量。
- 孤儿检查先校验费用标准属于同项目，再根据 `target_type` 条件关联资产或仪表，并校验互斥 ID、空 ID、非法类型和跨项目关系。
- 所有质量指标按顶部所选项目计算，不再把其他项目问题混入当前项目。

规范合成数据实时结果为：总分配 773、资产分配 743、仪表分配 30、孤儿 0；隔离项目总分配和孤儿均为 0。

### 2.4 房屋数量硬编码为 359

旧 API 已查询房屋数量，但前端质量项用 `rooms === 359` 作为通过条件；这会把种子样本数量误当成业务规则，并使其他项目必然失败。

修复后：

- API 使用条件计数从 `asset` 按当前项目实时统计 `enabled=TRUE` 的有效房屋和车位，归档资产不进入看板数量。
- 新增 `room_detail_mismatches`：启用房屋缺少房屋明细，或启用非房屋错误拥有房屋明细，均计为异常；已归档资产不再形成误报。
- 前端展示 API 返回的房屋数，质量项判断“房屋主档与明细一致性”是否为 0，不再出现 359 常量。
- 双项目回归同时断言主项目 359、隔离项目 1；若 UI 或 API 再次写死 359，测试会立即失败。

## 5. 使用与部署边界

- 当前可直接使用的是本机地址 `http://localhost:5174`；这是人工验收环境，不是公网生产地址。
- API 运行在 `http://localhost:8088`。生产部署不应直接暴露 API，也不应直接把 Web 明文端口开放到公网。
- 正式部署必须把候选镜像推送到受控注册表，使用 `registry/repository@sha256:<digest>`，在目标 Linux 主机按实际架构复扫，并通过仓库外 Secret、TLS 代理和部署前/后验证器。
- 当前业务数据仍是脱敏合成数据。目标系统真实住户、账务、第三方账号、Cookie、令牌和生产通道没有导入本工程。

## 6. 复发防护

- 报表字段契约同时由前端 serializer 单测、后端 22 报表矩阵、OpenAPI 漂移和浏览器生命周期约束。
- 报表及看板请求带项目代次保护；保存条件按项目/路由隔离，项目切换、响应乱序和损坏快照都有组件测试。
- 看板用两个数据量不同的项目做断言，防止重新写死主项目样本值。
- 费用分配测试同时存在 ASSET 和 METER 目标，防止再次用单表连接判断全部分配。
- Dockerfile 设置 OpenSSL 最低版本，候选构建使用无缓存安全刷新；最终发布必须扫描确切 image ID/digest。
- 扫描证据包含原始报告哈希并由验证器重算，不能仅手工修改汇总中的漏洞计数。
- 生产 Compose 的网络所有权、登录锁定、启动命令和健康检查既有静态负向样例，也在部署后按 Docker 实际配置复核。
