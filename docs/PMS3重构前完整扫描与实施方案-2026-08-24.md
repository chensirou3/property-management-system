## 1. 执行结论

### 1.1 一句话判断

当前工程已经是一个可运行的物业收费“演示型业务内核”，但不是目标 PMS3 的高保真复刻。它在基础档案、应收、收银、抄表和账务不变量方面有保留价值；在登录、导航壳层、页面交互、组织权限、报表体系、数据口径和真实数据迁移方面需要系统性重构。

### 1.2 推荐决策

建议选择“受控重构”，不建议继续以零散 CSS 修改和通用列表堆叠的方式补页面：

1. 保留现有 Vue 3、Java 17、MySQL、Flyway、账务不变量、幂等设计和模拟适配器作为技术与业务原型；
2. 重建登录页、蓝色顶栏、160px 深色侧栏、项目切换、多页签工作区和页面级交互组件；
3. 将 49 个目标页面按领域纵切实现，不再让大多数页面共用一个 `GenericDataView`；
4. 先建立目标数据的“口径字典 + 字段映射 + 迁移暂存区 + 对账规则”，再决定导入哪些真实数据；
5. 目标站真实数据只通过获得授权的官方导出/API/数据库备份迁移，开发环境继续使用脱敏或合成数据；
6. 在生产试点前完成认证语义、项目隔离、依赖漏洞、自动化测试、TLS、备份恢复和外部通道整改。

### 3.4 必须建立“数据口径层”

目标页面显示值与底层总量存在有意义的口径差异：

- 底层建筑类资产为 359；页面曾显示 353，差额与 6 个“其他”房间类别一致；
- 底层费用定义为 22；页面默认显示 11，与 11 个启用定义一致；
- 底层存在 1 个仪表关系；页面默认列表曾显示 0，可能受状态、资产范围或默认过滤影响；
- 页面“9 栋”可能包含 8 个住宅楼座和 1 个停车分组，而本地仅按住宅楼栋建模为 8。

因此每一个看板和报表指标必须有以下定义：名称、业务对象、过滤条件、时间口径、状态口径、去重键、金额精度、是否含冲正、SQL/查询版本和责任人。禁止直接用数据库 `COUNT(*)` 猜页面数字。

### 4.2 当前页面实现模型

本地导航包含 5 个一级分组、31 个叶子菜单。路由实现分为：

- 专用页面：项目看板、应收工作台、收银台；
- 抄表工作台：6 个菜单共享一个 `MeterWorkbenchView`；
- 其余约 22 个菜单：共享 `GenericDataView`，通过 `pageSchemas.ts` 切换列和表单。

`GenericDataView` 适合基础 CRUD 原型，但不能表达目标站中的树形房产工作区、多维筛选、批量费用分配、临时应收、票据换发、预收冲抵、复杂报表、打印布局和迁移连接器。继续扩展该组件会形成大量条件分支和不可维护的隐式页面协议。

### 5.4 后端与数据模型差距

当前 `DataResourceController` 把大量实体统一为 Map + 资源目录。它适合原型查询，但正式重构需要：

- 对组织、资产、客户关系、费用、账单、收款、预收、押金、票据、发票、日结和迁移建立明确 DTO 与领域服务；
- 读接口和写命令分离，复杂报表使用独立读模型；
- 每个写命令定义权限、幂等键、业务校验、审计事件和并发策略；
- 禁止前端直接决定金额、余额、账务状态和最终关联；
- 账单、支付、预收、押金、冲正和调账继续采用不可变流水与反向流水；
- 关键状态机版本化并通过数据库约束保护；
- 外部回调使用签名验证、事件去重、Outbox/Inbox 和重放机制；
- 大批量应收、导入、导出、打印和迁移改为异步任务。

## 6. 真实数据使用与迁移方案

### 6.1 是否可以使用目标数据

可以，但必须区分“用于理解系统”和“导入重构系统”两种用途：

1. 当前脱敏聚合可以立即用于容量、字段和关系设计；
2. 字典、状态、费用类别、单位、仪表类型等配置数据，在确认授权后可作为配置迁移候选；
3. 房产、客户、手机号、证件、车辆、账单、支付、发票和访客属于敏感或高风险数据，不能通过页面抓取直接复制到开发环境；
4. 正式迁移只能使用数据所有方批准的 API、数据库只读副本或官方导出文件；
5. 目标账号密码、Cookie 和令牌永不进入源码、数据库迁移文件或文档。

### 6.2 数据分级

| 等级 | 示例 | 开发环境 | 生产迁移要求 |
|---|---|---|---|
| C0 公共结构 | 菜单名、字段名、状态枚举 | 可使用 | 记录来源与版本 |
| C1 业务配置 | 费用定义、标准、字典、票据规则 | 脱敏后可使用 | 业务负责人审核、版本化 |
| C2 资产数据 | 楼栋、房屋、车位、仪表 | 使用映射后的假名数据 | 加密传输、访问审计、对账 |
| C3 个人信息 | 姓名、电话、证件、住址、访客 | 禁止进入普通开发库 | 最小化、加密、脱敏展示、保留期限 |
| C4 财务/税务 | 应收、实收、预收、押金、发票、银行 | 仅合成样本 | 双人复核、不可变原始区、逐笔/汇总对账 |
| C5 秘密 | 密码、Token、密钥、商户证书 | 禁止 | 密钥管理系统、轮换、永不导出明文 |

### 6.3 需要向数据所有方取得的资料

优先级从高到低：

1. 数据字典和每个字段的业务含义、唯一键、状态值、更新时间；
2. 小区—网格—楼栋—单元—房屋—车位—仪表的完整层级与稳定业务键；
3. 客户—资产关系的类型、起止时间、主业主/同住人/租户/历史关系；
4. 费用定义、标准版本、计算公式、精度、舍入、生效期、滞纳金和减免规则；
5. 应收、账单明细、收款分配、退款/冲正、预收、押金、票据、发票和日结模型；
6. 22 张查询报表的字段、筛选、公式、去重、时间切片和样例导出；
7. 用户、角色、组织、岗位、项目范围和操作权限矩阵；
8. 支付、发票、银行和 IoT 的接口文档、测试环境、签名规则和错误码；
9. 全量导出方式、增量字段、删除标记和可接受停机窗口；
10. 3–5 个已经人工核对的月份作为金标准对账样本。

### 6.4 迁移流水线

建议建立五层数据区：

```text
官方导出/API/只读副本
        ↓
Raw 原始不可变区（加密、只读、校验和）
        ↓
Quarantine 隔离区（格式校验、病毒扫描、错误行）
        ↓
Canonical 标准模型（字段映射、枚举转换、去重、主键映射）
        ↓
Staging 迁移暂存（业务校验、关系校验、差异报告）
        ↓
Production 正式库（批次提交、审计、可回滚）
```

每次迁移批次必须记录：来源文件/API、SHA-256、提取时间、源系统版本、行数、映射版本、错误数、导入数、跳过数、执行人、审核人和回滚点。

### 6.5 必须建立的映射表

- `migration_project_map`
- `migration_org_map`
- `migration_building_map`
- `migration_asset_map`
- `migration_customer_map`
- `migration_customer_asset_map`
- `migration_meter_map`
- `migration_fee_definition_map`
- `migration_fee_standard_map`

源 ID 只保存在受控映射表，不作为公开 API 的业务主键。正式系统使用内部 UUID/ULID 与稳定业务编号。

### 6.6 对账门槛

迁移通过至少需要：

- 数量：小区、楼栋、单元、资产、客户、关系、仪表、费用、账单、流水逐层核对；
- 关系：孤儿为 0，重复有效关系为 0，唯一键冲突为 0；
- 面积：按楼栋/资产类型汇总一致；
- 金额：按项目、账期、费用、资产、客户、支付方式、收款员和状态汇总一致；
- 账务恒等式：应收 = 已收 + 未收 + 合法调整；余额不得无依据为负；
- 时间：迁移截止点前后增量无丢失、无重复；
- 报表：金标准月份的 22 张报表在约定容差内一致；
- 抽样：高风险数据由业务、财务和技术三方联合抽样签字。

## 7. 目标架构

### 7.1 总体建议：模块化单体优先

当前团队和单项目规模不需要立即拆成大量微服务。建议使用模块化单体 + 明确领域边界 + 异步任务/Outbox：

```text
Vue 3 管理端
  ├─ 应用壳层与权限路由
  ├─ 领域页面组件
  ├─ 报表/打印/任务中心
  └─ 类型化 API 客户端
            ↓
Spring Boot 3.x（实施时选择受支持版本）
  ├─ IAM / Organization
  ├─ Property / Customer
  ├─ Fee / Receivable
  ├─ Cashier / Ledger
  ├─ Metering
  ├─ Reporting
  ├─ Migration / Integration
  └─ Audit / Task
            ↓
MySQL + Redis + Object Storage
  ├─ 业务写模型
  ├─ 报表读模型
  ├─ Outbox / Inbox
  └─ 迁移暂存区
```

只有当真实负载、团队边界或独立部署要求出现后，才拆分支付、报表、IoT 或迁移服务。

### 7.2 前端重构

- 保留 Vue 3 + TypeScript + Element Plus；
- 新建 `design-tokens`：颜色、字号、间距、边框、密度、状态色；
- 新建 `AppShell`：蓝色顶栏、160px 侧栏、项目选择、多页签、面包屑；
- 新建页面原语：`QueryPanel`、`DataGrid`、`TreeWorkspace`、`BatchActionBar`、`TaskDrawer`、`MoneyCell`、`StatusTag`；
- 对 49 页建立独立路由元数据、查询模型、列模型、权限和验收截图；
- 复杂页面使用专用 View/Composable；通用 CRUD 仅保留给低风险配置页；
- OpenAPI 客户端生成纳入 CI，并禁止前后端类型漂移；
- 导出、打印、上传统一走任务中心，不再用占位弹窗。

### 7.3 后端重构

- 从 Spring Boot 2.7 迁移到实施时受支持的 Spring Boot 3.x；
- 将 Map 型通用写接口限制在低风险配置，核心业务使用类型化命令；
- 使用 Bean Validation + 领域校验 + 数据库约束三层保护；
- 明确 401、403、409、422 等错误语义和统一错误体；
- 对费用生成、支付确认、回调、冲正、预收抵扣、押金退还、抄表入账使用幂等键；
- 建立报表读模型、快照表或可审计聚合，不用在线跨几十张表临时拼接；
- 建立异步任务状态机：待执行、执行中、成功、部分成功、失败、取消；
- 对外部系统采用端口/适配器，模拟与真实通道在部署配置和 UI 中清晰区分。

### 7.4 安全基线

- 全链路 HTTPS；
- 密码使用强哈希，密钥进入 Secret Manager，不落源码；
- 登录限流、失败审计、可选 MFA、会话撤销和短期访问令牌；
- RBAC + 组织/项目/小区数据范围，默认拒绝；
- 普通角色和第二项目必须进入自动化隔离测试；
- 个人信息按字段脱敏，导出加水印、审批、审计和有效期；
- 数据库账号最小权限，迁移账号与应用账号分离；
- Swagger、Actuator、任务管理和迁移中心禁止公网裸露；
- CI 生成 SBOM，执行 npm、Maven、镜像、Secret 和 SAST 扫描；
- 财务与配置高风险操作采用双人复核或审批流。

## 10. 上线、切换与回滚

### 10.1 推荐切换顺序

1. 冻结目标系统结构变更，保留日常业务；
2. 完成全量只读抽取并导入新系统；
3. 连续执行增量同步和自动对账；
4. 业务用户在新系统做平行只读核对；
5. 在约定窗口短暂停写目标系统；
6. 执行最后增量、账务对账和用户权限核对；
7. 新系统开放写入，旧系统转为只读；
8. 保留旧系统和原始导出满足审计期限；
9. 观察至少一个完整收费/日结周期后再决定退役。

### 10.2 回滚条件

出现以下任一情况立即停止切换或回滚：

- 账单、实收、预收、押金或日结出现无法解释的金额差异；
- 权限导致跨项目/跨组织数据泄露；
- 支付回调重复记账、漏记或无法重放；
- 数据迁移出现不可定位的丢失/重复；
- 关键报表不能在业务时限内生成；
- 备份无法恢复或审计链不完整。

回滚不应删除新系统数据，而应停止写入、保全证据、导出切换期间新增业务，再按预先演练的反向同步方案恢复旧系统。

## 12. 需要业务方确认但不阻塞当前开发的决策

1. “复刻”的验收重点：视觉 1:1、业务行为 1:1，还是两者同等；本方案默认两者同等，内部技术不照搬；
2. 预计企业数、小区数、并发用户、资产量、月账单量和报表时限；
3. 是否需要迁移全部历史账务，还是仅迁移余额 + 最近若干年明细；
4. 客户个人信息的合法处理范围、保留期限和脱敏规则；
5. 哪些支付、发票、银行和 IoT 厂商是首期范围；
6. 22 张报表中哪些属于财务法定/审计报表，哪些可后置；
7. 是否保留目标式多页签体验；本方案建议保留体验但不用 iframe；
8. 首个试点小区、金标准账期和业务验收负责人。

## 13. 重构完成定义

重构不能以“菜单已出现”或“页面能打开”为完成。每个页面必须同时具备：

- 目标式视觉和可用的响应式/最低分辨率表现；
- 已签字的字段、筛选、操作、状态、权限和口径；
- 类型化 API、业务校验、数据库约束和审计；
- 加载、空、错误、无权限、冲突和批量部分失败状态；
- 单元/组件/API/E2E/视觉测试；
- 导入导出、脱敏、打印和任务结果（如页面需要）；
- 生产监控指标、结构化日志和请求追踪；
- 数据迁移映射、对账结果和回滚说明；
- 文档、操作手册和业务验收记录。

## 14. 最终建议

可以在现有工程上继续，但应把它定位为“可复用业务原型”，而不是继续宣称为已完成复刻。最佳路线是：

1. 先用 1–2 周修复工程治理和自动化基线；
2. 用 2–3 周完成目标式壳层与权限模型，建立视觉和架构样板；
3. 以房产—客户—费用—应收—收银这一条真实纵向链路作为第一期；
4. 只迁移经过授权、映射和对账的数据，开发测试不使用原始住户与财务明细；
5. 把 22 张报表和外部通道当作独立工作流，而不是通用表格的附属按钮；
6. 通过平行运行和金标准账期验证后，才进入生产切换。

这个方案既能保留当前已经验证的账务、幂等和抄表内核，也能解决用户已经观察到的 UI、页面行为和数据真实性问题。
